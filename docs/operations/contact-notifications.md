## Persistence, retries and limits

- Six fields are stored in the existing private `form-submissions.submissionData` array; no database migration. Existing submissions are not rewritten. A read-back must match before success is returned.
- UUID request receipts suppress sequential request replays; an interrupted first attempt can recover its missed notification using the same Resend key. Client submit locking prevents double clicks. Persistent counters limit a saved email to one inquiry/minute and five/hour; on Vercel, a daily HMAC of the platform-controlled IP supports ten/hour. Raw IPs are not saved or sent in notifications. These are application limits, not a DDoS service or an atomic concurrent-request guarantee.
- The existing honeypot is now `contact_check`, leaving `website` available for the genuine optional URL. Service is allowlisted, URLs permit only HTTP(S) without embedded credentials, and all fields have server-side length/format checks. Submitted URLs are never fetched.
- A provider error cannot discard a saved inquiry. Success says **saved**, never **email delivered**. Notification status (`not_configured`, `accepted`, `failed`) and provider message ID are kept in the private submission record. API acceptance is not proof that either inbox received the message.
- Resend request idempotency uses the Payload submission ID and sends both recipients in one request. Resend deduplicates this key for 24 hours. This is deliberately separate from application form replay detection.
- Operator retry, dry-run by default: `NODE_ENV=production VERCEL=1 node --import=tsx scripts/retry-inquiry-notification.ts <id>`. Add `--send` only after configuration and verification. Accepted records are not resent; uncertain old attempts require manual provider-history review. There is no new scheduler/background retry infrastructure.
