# Dependency security remediation and mobile performance

November 18, 2026 (Chicago). Production baseline `bc5f103`; compatible first release `385eb16`. Scope: existing Dash 10 Studio Next.js/Payload deployment. No exploit attempts or claims about prior compromise. All 10 critical and 36 high original advisories were inspected against primary maintainer/GitHub descriptions, actual configuration and installed paths. [Full paths and ranges](2026-11-18-security-advisories.json) accompany the matrix below.

## Security outcome and priorities

Original production-tree audit: **10 critical / 36 high / 35 moderate / 12 low**. Final approved candidate: **0 critical / 2 high / 1 moderate / 0 low**. Full tree including development dependencies: **0 critical / 2 high / 7 moderate / 0 low**. Counts are advisory records, not demonstrated exploits. Audit exits nonzero while findings remain; there is no claim of a clean audit.

Highest-priority original production risks were Payload Postgres SQL injection (public readable collections with dynamic filters), Form Builder RCE (plugin/submissions enabled), Payload multipart parsing DoS, and Next Server Action DoS (inquiry action enabled). All are patched in the candidate. Image-decoder issues were conditional on malicious media input; staff-only uploads reduced exposure but were not a patch. Both Next and Payload image processing now resolve Sharp 0.35.5. Windows-only RCE, absent OG/cache features, unused API-key/JWT mapping and disabled orderable configurations were distinguished from reachable request paths, without dismissing upgrades.

Updated coherently: all Payload packages 3.87.1 → **3.90.0**, Next 16.2.6 → **16.4.5** with matching lint config, Sharp 0.34.2 → **0.35.5**. Same-major transitive refreshes plus narrow Undici 7.30.1, source-map-js 1.2.2, DOMPurify 3.4.17 and fast-copy 3.1.0 overrides address pinned packages. Vitest 4.1.0 and same-major brace-expansion/Vite patches address development findings. No forced audit fix or blind major framework upgrade.

### Remaining risks and mitigations

- **Happy DOM 20.14.6: two high records.** It is a server-capable Lexical dependency, not automatically test-only. The RCE requires attacker module evaluation; SSRF requires parsing attacker iframe/stylesheet HTML. No application or Payload integration imports `@lexical/headless/dom`; the headless editor entry used here imports only Lexical, not Happy DOM. App conversion uses explicitly supplied JSDOM. No public route evaluating arbitrary HTML/JS with Happy DOM was found. Do not add such a route or enable evaluation/resource loading. The advisory's same-major patched 20.14.7 is unavailable in the registry. A 21.0.4 major override needs separate upstream compatibility review/approval; it was not forced. Prefer an upstream Lexical/Payload release adopting the fix. This is a reachability assessment, not proof against every future path.
- **esbuild 0.18.20: one moderate production-tree record**, through Postgres adapter → Drizzle migration tooling → old esbuild-kit loader. Its vulnerable HTTP development-server feature is not run by Vercel request handlers. Keep tooling local/unexposed; upgrade with the supported Drizzle toolchain rather than forcing a breaking pre-1.0 esbuild into it.
- Full-tree moderate findings additionally affect development tooling. No dev/test server was added to production. Existing operational findings (durable CMS media storage, email delivery configuration, preview-secret rotation, full script CSP and retention/spam workflow) remain in the preceding quality audit and are not silently claimed fixed here.

## Approved migration and content preservation

It is idempotent; no destructive down migration, automatic schema push or database reset. New nullable column is backward-compatible with the prior deployment.

Private read-only before/after snapshots of 28 article/page/category and version/relation tables have identical SHA-256 content hashes. Existing posts **2, 3, 4**, publication status, dates, prose, Lexical JSON, SEO and versions are unchanged. User count remains one; no credentials or inquiry data were exported. Snapshots are Git ignored and mode 0600. New generated Payload types add the reset-request field and reflect the schedule-publish task user-reference shape; no pending content was rewritten. Import map regeneration reports no new imports.

The upgraded Lexical parses the exact stored JSON for all three articles and preserves the text sequence; HTML renders successfully. Uploaded Markdown conversion still passes word-for-word checks (1,017 / 990 / 970 words), including tables, headings, lists and links. These checks do not save/reimport posts. ## Mobile bottleneck and incremental changes

Actual LCP node: `video.dash-hero-video`; LCP resource URL is the **poster**, not the MP4. Fresh pre-change production Lighthouse 13.6.0/default simulated-mobile sample: **6.055s LCP / Performance 77**. Previous audit: 5.705s / 79. Observed native timings in Lighthouse insights are different from its simulated LCP and are not mixed.

Three comparable real-throttled production Chrome baseline samples: **4.212s, 4.216s, 4.084s**, median **4.212s**. Fresh profiles, 412×915, 4× CPU, 150ms network latency, 196,608 download bytes/sec, cache disabled. First sample wire totals: fonts 258,728B, JS 269,036B, stylesheet/link 21,687B, poster 86,826B, MP4 770,565B. Poster was discoverable/high priority; initial fonts, scripts and video competed for mobile bandwidth. CSS is render-blocking. Lighthouse estimated ~95KB unused initial JS (~450ms simulated LCP opportunity in a local diagnostic run). No Google/HubSpot request occurs before consent, so tracking does not explain the clean first-visit baseline.

- Added approved-font Latin/punctuation/technical-symbol WOFF2 subsets, ~100KB combined instead of ~258KB. Retained glyph outlines match; full complementary unicode-range faces preserve other scripts. Explicit ranges also avoid downloading full fonts to search for unsupported glyphs.
- Deferred decorative MP4 source attachment until window load plus two animation frames, allowing initial resources/poster to paint first. Existing framing, overlays, once-only playback/rate, pause and final-frame hold remain. Reduced motion requests no MP4. No re-encoding; server HTML/content/poster remain available without JS.
- Kept existing poster (~85KB), CSS and architecture. An AVIF experiment saved little at comparable quality and was not shipped. The root homepage now renders the existing StudioHome directly instead of re-exporting the generic CMS [slug] page. This removes unused generic form, syntax-highlighting and preview dependencies from its initial route bundle; CMS supporting routes and metadata are unchanged. The isolated build has 13 initial scripts totaling 203,772 bytes gzip and no Prism code in that set. No redesign or large dependency added.

Local diagnostic samples are not production comparisons; the intermediate candidate measured 4.286s/86 while a needless fallback font still loaded. Live after-release results follow below. No 2.5s or field-CWV pass is claimed without evidence.
